# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A real-time, always-on digital ant colony simulation (Canvas2D, vanilla JS ES modules, zero dependencies, no build step). Intended as an ambient screen you can leave running — see section on design philosophy below.

## Running it

There is no build/test/lint tooling (no `package.json`). To run:

```bash
python -m http.server 8000
```

Then open `http://localhost:8000`. **Do not open `index.html` via `file://`** — ES module imports fail silently under `file://` (blank canvas, check the browser console).

Controls: Click = spawn food at cursor (surface view only). Shift+Click = place a circular obstacle (surface view only). `T` = toggle pheromone trail overlay (visual only, doesn't affect simulation). `V` = toggle between the surface and underground views (visual only — the simulation keeps running in both regardless of which is on screen). `F` = cycle fast-forward (1x → 2x → 4x → 8x → 16x → 1x, labelled in the top-left whenever it isn't 1x).

Fast-forward is the one control that isn't purely visual, and it's worth understanding why it's safe: it runs *more* fixed `SIM_DT` steps per frame and never touches the step itself, so a colony run at 16x is bit-for-bit a colony left running at 1x for the same simulated time. It's also the practical way to see anything on this project's timescale — a chamber is minutes of digging, and the nursery filling enough to make the colony deepen the nest is the better part of an hour.

## Design philosophy (read before adding features)

The interaction model is **stewardship, not control** — the player nudges the colony (drop food, place obstacles, toggle views) and never commands individual ants directly. The goal is to approximate real ant-keeping, not to build a pathfinding tech demo; ants use proximity-based sensing and pheromone trails, not pathfinding. Idle/non-interaction time should still feel alive.

See `ROADMAP.md` for the current plan and priorities (colony growth — queen, brood, food economy, and a new underground tunnel system the queen/brood will live in — is the active focus; movement/foraging/pheromones are already deep).

## Architecture

```
index.html   — canvas element, loads src/main.js as the sole module entry point
src/
  config.js       — every tunable constant, including the full colour palette for both views; single source of truth, nothing hardcodes a tuning value elsewhere
  ants.js         — SoA (Structure-of-Arrays) typed-array store for ants + spawn/kill
  behaviors.js    — generic movement primitives: wander, avoidSurfaces, separationSteer, integrate
  foraging.js     — task state machine: food/nest detection, seek-steering, pickup/dropoff
  world.js        — environment data: nest, food sources, obstacles
  colony.js       — colony-level state, store only: the shared food store, the queen, and the brood array
  queen.js        — what the queen does: lays eggs against the nest's food, walks down if the nest deepens past her
  underground.js  — underground tunnel grid (dirt/tunnel cells), entrance linkage, tunnel-wall avoidance
  nestPlan.js     — what the colony needs excavated and where: chamber registry, demand rules, one active project at a time
  digging.js      — the DIG task: recruitment, entrance crossing, claiming and carving one planned cell at a time
  spoil.js        — the excavated earth: the crater of dumped soil that builds up around the entrance
  provisioning.js — the STORE task: carrying a forager's load down into the nest and handing it over at a chamber
  pheromones.js   — trail grid: deposit/decay/diffuse/sample/follow
  spatialGrid.js  — coarse ant-position binning for fast neighbor queries
  sim.js          — per-tick orchestration; decides which behaviors run per ant state
  render.js       — surface drawing, plus the surface/underground view dispatcher; reads ant state, never mutates it
  undergroundRender.js — underground view drawing (dirt/tunnel cells, entrance, unlocked-region boundary)
  main.js         — wiring, input handling, fixed-timestep loop, init
```

**File ownership is strict** — each file owns one concern and nothing reaches into another's internals directly. Respect this when extending: new concerns get new files (e.g. a hypothetical nursing behavior would be `nursing.js`, not folded into `foraging.js`).

### Core architectural decisions

- **Structure-of-Arrays for ants, not per-ant objects.** `ants.x`, `ants.y`, `ants.rotation`, etc. are parallel typed arrays (`ants.js`), chosen for scale — the simulation targets up to `MAX_ANTS` (currently 10,000). Match structure to actual scale for new entity types rather than defaulting to SoA everywhere (e.g. `spatialGrid.js` uses a plain `Map` since simplicity mattered more than raw throughput there).
- **Ant array index is not stable identity.** `killAnt()` does swap-and-pop, so an index can silently refer to a different ant next tick. Anything that needs to reference a specific ant persistently must use `ants.id[i]` plus the `idToIndex` Map, never a raw index.
- **Fixed timestep simulation, decoupled from render rate.** `main.js`'s `frame()` runs an accumulator loop; `simStep(dt)` always advances in fixed `SIM_DT` (`1/60`s) chunks regardless of actual frame rate. Render runs once per animation frame at whatever rate the display allows.
- **Steering is additive and compositional.** Nearly every behavior follows the same pattern: compute a desired angle, take the normalized angle difference from current heading (`Math.atan2(Math.sin(diff), Math.cos(diff))`), nudge `rotation` by `diff * steerRate * dt`. Multiple behaviors (wander, avoidSurfaces, separationSteer, followTrail, seek) stack additively within one tick — see `sim.js` for the per-tick order.
- **Walls and obstacles are one unified avoidance system** (`avoidSurfaces()` in `behaviors.js`), not two independent systems. They used to be separate and could fight each other where a rock sat near a wall; now every nearby surface (4 walls + every obstacle) contributes to one combined push vector before a single steering correction is applied. When adding new surface-like hazards, fold them into this function rather than writing a parallel avoidance path.
- **Digging is demand-driven, and the decision lives above the ant.** `nestPlan.js` decides *what* the colony excavates (only once a demand rule says it needs the space, one project at a time, cooldown between); `digging.js` decides only how one ant carries that out (claim a cell, walk to it, carve it). An ant never picks a cell to dig on its own initiative, and with every need met, nobody digs at all. This replaced "carve the nearest reachable dirt," which eroded a shapeless blob outward from the entrance.
- **The nest is organized by DEPTH, and a chamber's purpose is derived from it, never stored.** A single mostly-vertical shaft descends from the entrance (zig-zagging, steepening with depth); chambers hang off it on short lateral stubs. Depth then decides everything else: radius decays geometrically with depth (shallow rooms several times the area of deep ones), inter-chamber spacing widens with depth, and `purposeOf(chamber)` reads the room's job off its depth band — atrium on top, stores strictly in the middle, brood and the queen in the bottom third. **The queen's chamber is not a purpose, it's a position: the deepest chamber.** Consequences worth knowing before you touch `nestPlan.js`:
  - Deriving purpose rather than freezing it at dig time is load-bearing. It's what lets the founding chamber start as the whole nest (deepest, so the queen's) and become a store, then an atrium, as the colony digs below it — which is what real founding chambers do. It also makes non-interleaving strata a *property* rather than a rule to enforce, since depth-fraction rises monotonically and the thresholds are ordered. Freezing purpose instead caused stranded mislabelled rooms, brood chambers that "expired" as the shaft grew under them, and runaway excavation to the floor of the world.
  - **Demand is for chamber AREA per stratum, not a count of rooms.** A count can be geometrically impossible to satisfy in a bounded world, and can't be satisfied by *widening* a room — which would make enlargement dead code.
  - Nests grow three ways, tried in that order: a new room, then **enlarging** an existing one (the dominant mode in real nests), then deepening. Deepening is capped allometrically by population (10x the workers buys only ~2.4x the depth), so a growing colony gets space from more and bigger rooms rather than a longer shaft. Removing that cap re-introduces erosion to the world floor.
  - Needs are walked in priority order and the first *plannable* one wins. Taking only the most urgent need and giving up if it can't be sited starves everything below it forever.
  - A single shaft caps how many rooms a nest can host, so mature-nest statistics (shallow/deep area ratio, ~half the area in the top quarter) are only approached, not reached. Branch shafts are the real fix — see `ROADMAP.md` Phase B2.
- **Excavation is slow on purpose.** One cell takes `DIG_CARVE_MIN..MAX` (~10-15s), so a chamber is minutes of work for a whole dig force — an ambient-timescale activity, matching the project's "leave it running" framing rather than something you watch complete. Anything that makes a long carve look like a hung ant (e.g. removing the per-cell progress shading `underground.js` tracks for the renderer) is a regression, not a cleanup.
- **The ant sprite is a black silhouette with no outline, which constrains the whole palette.** An ant is only as visible as the ground behind it, so both views paint their own *light* ground (`GROUND_COLOR` / `UNDERGROUND_TUNNEL_COLOR`) and every colour lives in one palette section in `config.js` — the two views have to be picked together. This is why the underground reads "inverted" from a real formicarium photo: dug galleries are the light surface and packed earth is the dark mass, because the original way round (mid-brown dirt, near-black tunnels) put black ants on near-black ground in the exact spaces they spend their time. Don't darken a surface ants walk on.
- **Long pauses need visible motion.** A digger holds still for a whole carve, so it twitches (`DIG_TWITCH_*`, applied in `sim.js`) the way idle and handling ants do — faster and smaller than the idle twitch, reading as scraping rather than glancing around. Any future state that freezes an ant for more than a moment needs the same treatment, or it looks like a bug.
- **No pathfinding on the surface; inside the nest, ants follow the shaft.** The underground is a structure the colony built and every ant knows, so `routeWaypoint()` (`nestPlan.js`) routes along it: the mouth of the stub you're standing in, the shaft corners between here and there, then the destination's stub mouth — and it returns the *furthest via-point the ant can see in a straight line*. That last rule is what makes it robust: the ant always aims at somewhere it can actually walk to, cuts corners whenever geometry allows, and can never be sent at a point behind a wall. This is deliberately not general pathfinding and shouldn't become it — real ants get around their own nests by wall-following and familiarity.
  - It exists because every chamber hangs off the shaft on a stub, so the route between a room and anywhere else is an L, and straight-line seeking cannot turn a corner. Ants beelined into chamber walls and orbited until a give-up timeout fired: worst-case trips were 30-45s with regular timeouts, against ~5s now with none.
  - Both ends need their stub mouth, and the destination's is the one that's easy to forget — an ant already in the shaft alongside its target has no corners between it and the target, so omitting it collapses the route back to the beeline.
  - Simpler variants were tried and are worse: stepping a fixed distance in depth cuts through the earth between two zigs, and stepping corner-by-corner leaves ants oscillating between two nodes.
  - **Routing must include the room currently being excavated.** A chamber isn't registered until its last cell is open, so while it's being dug it's invisible to `chambers[]` — and diggers heading for the final cells of a nearly-finished room had no stub mouth to route through, so they beelined at a target around the corner and orbited the wall. `roomAt()` therefore checks the active project too. This was the last 4% of digger give-ups; with it they are zero.
  - **A digger's target is dirt by definition**, so the visibility check takes a `targetSlack` argument and stops short of the face. Without it the check can never succeed for a dig target and the router sends diggers away from cells they are standing next to — measured, 77% of diggers abandoned their claim, against 4% with the slack.
- **No pathfinding.** Ants use proximity detection (`SENSE_RADIUS`) plus straight-line seek-steering toward a believed target, path integration (dead reckoning via `homeVectorX/Y`) for returning to the nest, and pheromone trail-following (3-point sensor sampling) for recruitment. Delivery is not guaranteed — a lost carrying ant can wander indefinitely; this is accepted, not a bug.
- **`STATE_HANDLING` is now pickup only.** It used to serve both ends of the trip, disambiguated by the `carrying` flag. The dropoff end no longer pauses at the nest at all: food doesn't enter the colony at the entrance any more, so a returning forager walks straight in and the handover pause happens at the chamber where the food actually changes hands (`provisioning.js`, `STATE_STORE`).
- **The queen is a position, and she is the food economy's only sink.** She isn't in the `ants.js` SoA store — she has no task state, no wander, no path integration, so one plain object in `colony.js` is the right shape, and her behaviour lives in `queen.js` (the same store/behaviour split as `ants.js`/`behaviors.js`). Three things about her are load-bearing:
  - **Her chamber is the deepest one, not a room she owns.** As the colony digs below her the bottom of the nest moves, and she walks down to it along `routeWaypoint()` rather than snapping there. On an always-on ambient screen a teleport is a visible glitch; her walk is also the only movement code in the project that has no avoidance at all, just a refusal to step into a cell that isn't tunnel — the "prefer a hard clamp over a cleverer controller" rule, taken to its end.
  - **Every egg costs food out of the chambers** (`takeNestFood()`), with `colony.food` mirrored down. Before this nothing consumed food at all: the counter only rose, storage demand was unbounded, and the deepest chamber became a larder that grew forever. Any future consumer should spend the same way — from the rooms, not from the headline number.
  - **Eggs go to the brood stratum, not only to her room.** Real workers lift eggs off the queen as fast as she lays; until nurses exist (Phase E) `chooseBroodChamber()` stands in for that. It matters mechanically too: without it a full room stops her laying permanently, and `BROOD_AREA_PER_BROOD` must stay larger than `BROOD_PACK_AREA` for the same reason — a nursery packed to capacity has to still generate demand for more nursery.
- **Food physically travels into the nest.** A forager's load is carried down to a chamber rather than evaporating into a number at the surface. Where it goes follows the biology: food goes where it is *consumed*, so a store chamber is a preference (used if one has room) and the fallback is the deepest chamber, where the brood and queen live. Most ants don't warehouse food in rooms at all — dedicated granaries are a granivore speciality — so storage must not be modeled as the default destination.
- **The entrance marker is cosmetic; arrival radii are not derived from it.** `NEST_ARRIVE_RADIUS` was once `NEST_DRAW_RADIUS + ANT_LENGTH`, which tied how precisely ants had to arrive to how big the entrance was *drawn*. They're independent now — shrinking the marker to a realistic hole must not retune every forager and digger approach.
- **Time-dependent randomness must be tick-rate independent.** Noise scales with `sqrt(dt)` (e.g. wander's random walk), decay uses proper exponential decay (`Math.exp(-rate * dt)`, e.g. pheromone decay), not linear-per-frame approximations.
- **World size == viewport size**, currently. No camera/pan/zoom. Nest, food, and obstacle positions do not adapt to window resize (accepted limitation); the pheromone grid *does* reinitialize on resize (clears the trail, but avoids a worse bug: stale grid dimensions otherwise cause misaligned cell-to-world mapping and a visibly distorted trail overlay).

### Debugging lessons for steering code specifically

If you're touching `behaviors.js`, `foraging.js`, or `pheromones.js` steering logic:

1. Steering rates need a decisive margin over competing forces, not a narrow one — undershooting this has repeatedly caused visible wall-hugging/trail-following/obstacle-avoidance failures.
2. A strong *base* (non-urgency) steering rate can trap an agent in a stable orbit around a circular obstacle — circles have no corner to force an exit. Keep the base rate loose; reserve strength for the urgency/danger-driven term (see `AVOID_STEER_BASE` vs `AVOID_STEER_URGENCY` in `config.js`).
3. Sign/direction-convention bugs are easy to introduce when reusing a steering formula with a differently-signed variable — a wrong sign can look like "not strong enough" when it's actually "pointing the wrong way."
4. When summing avoidance contributions from multiple nearby surfaces, sum the radial push vectors first (always adds coherently), then choose one tangent direction from the combined result — choosing tangents independently per-surface can cancel unpredictably at notches between obstacles.
5. **The underground is not the surface with different constants.** Every `TUNNEL_*` value was seeded from its `AVOID_*` counterpart, and at least one was actively wrong there: `TUNNEL_AVOID_HUG_FRACTION` at 0.85 (correct on the surface, where following an edge is useful) set the target standoff from a dirt face to ~1.8px, so ants pressed flat against tunnel walls and their sprite was drawn mostly over solid earth — this read as "ants get stuck in the dirt" and no centre-position metric could see it, because the centre was in legal open tunnel 100% of the time while 91% of bodies overlapped dirt. Dropping it to 0.2 also cut heading reversals ~4x and raised dig throughput several-fold: ants had been grinding along walls instead of walking. The remaining inherited values (margin, steer base, steer urgency) have not had this scrutiny.
6. **The underground is a domain where agents deliberately approach the hazard.** Every dig target *is* a dirt cell, so any avoidance behaviour strong enough to matter will fight the seek-steering that sent the ant there — and avoidance wins. A forward-probe "feeler" was built to fix the corridor-cancellation problem below and had to be deleted for exactly this reason; `config.js` carries a note where its constants were so it doesn't get reinvented. Prefer a hard position clamp (see `pushOutOfDirt`) over a cleverer controller.
7. **A frozen ant still needs the position backstops.** `sim.js`'s frozen paths (`STATE_HANDLING`, idle, and mid-carve `STATE_DIG`) `continue` before the movement tail, which silently exempted carving ants from the dirt clamp for the entire 9-16s of a carve — the worst possible place for that gap, since a carver is the one ant guaranteed to be standing against a dirt face and it holds still long enough to be seen. Any new frozen state needs the same treatment.
8. **`avoidTunnelWalls()` goes silent in corridors, by construction.** A corridor is `2*NEST_TUNNEL_RADIUS` (20px) wide against a `TUNNEL_AVOID_MARGIN` of 12, so dirt sits within margin on both sides and the summed push cancels to zero. This was written off in a comment as a rare symmetric squeeze; it is the normal case for every corridor in the nest. What makes it safe is the hard clamp, not the steering.
9. **Wall-hugging can hijack a task-committed ant, and a corner can hold it there forever.** `avoidSurfaces()` picks whichever tangent best matches current heading, so hugging *preserves* the direction of travel — an ant that touches a wall while seeking a target gets carried along it, with the urgency term (12) beating `SEEK_STEER_RATE` (3.5) the whole way, sometimes to the far corner, where the steering settles into a stable equilibrium pointing into the corner (position pinned by the hard clamp). WANDER ants escape via wander noise; task states have none, so they stay. This is why any long-lived seek-to-a-point task needs a give-up timeout (see `DIG_TRAVEL_TIMEOUT`) rather than assuming it will eventually arrive — it surfaced with diggers walking to the corner-placed nest, but nothing about it is dig-specific.

## Current known limitations (accepted, not bugs)

- No camera/pan/zoom; no obstacle removal interaction.
- Only one shaft, so no parallel chamber series and no branching — which caps how many rooms a nest can hold and keeps a mature nest from reaching the real top-heavy area distribution (see `ROADMAP.md` Phase B2).
- Chamber sites are still rejection-sampled within their depth band, so layout is organic rather than architected; the shaft is a real structure now, but there's no notion of tunnels reusing an existing corridor. Stubs are short by construction, so nothing long cuts across older tunnels any more.
- A digger's claimed cell can be genuinely unreachable by straight-line steering (a chamber around a bend), which is what `DIG_TRAVEL_TIMEOUT`/`DIG_EXIT_TIMEOUT` exist to bound — accepted for the same reason lost foragers are.
- No player action to expand or shape the nest — digging responds only to colony demand (see `nestPlan.js`); the earlier "unlocked diggable region" cap was removed rather than wired to input.
- Single pheromone type (no directional/"no-entry" signal).
- `spatialGrid.js` uses a `Map`, not a flat typed array — a possible future optimization if it becomes a measured bottleneck.
- No population growth over time yet — brood accumulates and never hatches, because the stage machine (`egg → larva → pupa → adult`) is Phase D. Population is fixed at spawn via `INITIAL_ANT_COUNT`; `MAX_ANTS`/`INITIAL_ANT_COUNT` are configured with headroom between them specifically to leave room for runtime spawning when Phase D lands.
- Brood stays where it was laid. A chamber's purpose is derived from depth, so a room the colony digs below stops being nursery — but the eggs in it don't move, because nothing can carry brood until Phase D/E. Expect to see a pile of eggs in a room labelled "stores" in a nest that has deepened since.
- `colony.food` is now spent (by the queen) but not yet *bounded* by that spending: one egg per ~35s eats ~3.4 food/minute against an income that a generously-fed colony pushes an order of magnitude higher. Storage demand therefore still grows under heavy feeding. Larvae eating (Phase D/E) is the rest of the sink.
- `assets/` contains only the 6-frame walk-cycle sprite (`ant_0.png`..`ant_5.png`); the shadow-drawing code in `render.js` exists but is currently commented out/disabled.
